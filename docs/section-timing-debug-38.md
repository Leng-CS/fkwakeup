# #38 节次时间表调试记录

- Issue：https://github.com/Leng-CS/fkwakeup/issues/38
- 分支：`fix/section-timing-save`，基线：`2417973`
- 环境：Pixel_8_API_35 / Android 15 模拟器，2026-09-22。
- 测试前通过 `run-as` 备份测试 App 数据；复现崩溃后从备份恢复，再安装修复 APK 复测。

## 分步复现及结论

1. 基线 APK：课程管理 → 节次时间表 → 单节时长 45 改 47 → 确定。
   第 1 节为 08:00–08:47，第 2 节为 08:57–09:44；合法全局规则本身会触发重算。
2. 滚到底部点击保存：进程崩溃。logcat 时间 09:54:00.846：
   `SQLiteConstraintException: FOREIGN KEY constraint failed (code 787 SQLITE_CONSTRAINT_FOREIGNKEY)`，
   调用栈包含 `SectionTemplateDao_Impl` 的插入操作。
3. 重启：左侧节次时间消失，课程块以「第1节 / 第9节」替代具体开始时间。
   编辑器输出 `termId=0`，Repository 原先直接使用这个 ID 插入；删除旧表和插入新表分开提交，
   因此外键失败发生时旧表已经丢失。不是课程被删除。
4. 代码检查发现「未改开始时间也新增断点」：打开自动节次直接确认或只改结束时间，
   都会把该节固定下来，后续全局规则不再调整该节开始时间，甚至因此产生冲突。
5. 全局时长弹窗原先把滚轮和错误文字作为同级内容放入 AlertDialog 的 text 槽，
   未用 Column 分开布局；改为垂直排列，确保被拒绝的规则有清晰原因。

## 修复与保护

- Repository 将所有草稿统一绑定传入的目标学期；拒绝空表、非连续/重复节次及重叠时间。
- 起止分钟及单节顺序继续使用 `SectionTemplate` 已有校验，不修改数据契约。
- DAO 的删除、插入使用同一个 Room 事务；异常回滚全部修改，观察者不再收到中间空表。
- 保存/恢复默认失败时提示并保留旧表，协程取消正常向上传播；保存成功后触发小组件更新。
- 只有开始时间实际改变才新增断点；保留默认课表和用户明确设置的断点语义。

  第 2 节仍变为 08:57–09:44；保存显示「已保存」，强制停止并重启后周视图仍显示 08:57、10:57、14:57 等新时间。

  提示位于滚轮下方，无重叠；取消后保留 47 分钟设置。
- `git diff --check` 通过。

## 已损坏时间表的恢复边界

旧版已删除的自定义时间无法自动还原。升级后进入节次时间表重新配置并保存，
或点「恢复默认」重建时间表；课程与时间段记录保留。未擅自用默认值覆盖已有自定义配置。
